No source repository production target, provider credentials or enabled workflow is invented. Direct programmatic fixtures are implementation evidence; the CLI accepts only authenticated coordinator delivery.

## Acceptance criteria

1. **AC-1**: Disabled/incomplete policy, unpinned executable/script inputs, foreign delivery or store and unrelated SQLite reject before deployment. Actual pinned adapter subprocess receives only dedicated deployment credentials with bounded execution.
2. **AC-2**: Observe approved baseline then each progressive stage against complete service-bound fresh SLO metrics. Healthy real HTTP fixture rollout reaches 100%; terminal duplicate delivery returns recorded evidence with no extra effects.
3. **AC-3**: A real HTTP unhealthy candidate breaches the gate, restores the recorded known-good SHA and confirms measured restored health before recording rollback.
4. **AC-4**: Persist intent before effect, serialize unresolved operations, and reconcile lost deploy/rollback acknowledgements after private SQLite reopen through exact lookup without blind replay. Unknown effects fence subsequent releases.
5. **AC-5**: Malformed identity, stale or incomplete metrics cannot certify release. Private state retains precise release outcomes; CLI has no caller proof/adapter override and requires authenticated coordinator receipts. Neutral adopter configuration remains disabled; fixture proof does not activate production or claim independent review.
