# Reusable factory adoption

The harness supplies engineering workflow, protected verification/merge contracts, runtime recovery, optional delivery reporting and feedback contracts. New and existing repositories supply their own approved specs/tasks, identity, stacks, credentials and deployment profiles. `qyndex/claude-init` is the distribution source, not the required adopter repository or Slack destination.

The installer accepts a branch, tag or full commit SHA in `CLAUDE_INIT_REF`, fetches that ref only and prints its resolved immutable commit. A wrong ref blocks before reconciliation. Prefer a reviewed full SHA for reproducible rollout. Run from the target root or set INTO to it; linked worktrees are supported. Commit/stash staged, unstaged and untracked changes first. YES=1 explicitly permits a dirty target; YES=0 does not. UPGRADE and SKIP_SETUP likewise require exact 0/1.

The wrapper returns nonzero on setup failure and leaves the resulting candidate available for inspection/recovery. SKIP_SETUP=1 intentionally performs reconciliation only; it does not prove the adopter is configured or factory-ready. This version tests wrapper behavior against disposable local Git fixtures, including a stub reconciler/setup. It does not establish safe reconciliation of every real source file.

Remaining F-07 work: versioned file ownership, preserving customized upgrades, rollback/recovery of partial writes, excluding distribution specs/tasks/history/local memory, neutral target factory policy/config generation, runtime/stack capability checks, quota routing and evidence privacy/retention. The existing reconciler still contains broad overwrite/suppressed-copy paths; do not infer safe full upgrades from the wrapper tests. Factory authority stays disabled until target-specific protections and independent proof pass.

Reporting is optional per adopter. Configure its default-branch workflow, exclusive reporting runner policy, persistent private state and environment credentials using FACTORY-REPORTING-SETUP.md. The qyndex environment/channel/team record is an optional pilot record and must not become installer defaults. No target deployment or Slack send is performed by these installation fixtures. Production release support likewise requires each adopter’s separately proven service/metrics/rollback adapter; copying the harness never enables production autonomy.
