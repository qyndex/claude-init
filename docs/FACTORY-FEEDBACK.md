# Operator feedback and amendments

The reusable feedback core lives in `.claude/scripts/factory-feedback.py`. Its SQLite tables are a protected runtime projection, not a replacement for `tasks/TASKS.md`. The APIs run only within the trusted operator/coordinator boundary. They are not a network endpoint. Candidate code must not write this database or the approval document.

`Feedback(database, repository).intake(reporting_database, document)` requires a confirmed digest from the protected reporting database and explicit PR identities in that report. Documents retain exact text, reporter, classification (`defect`, `enhancement`, `requirement`, `priority`, `acceptance`), source reference, digest key and repository. Source references must come from an authenticated operator adapter; a caller-supplied reporter string alone does not establish authentication. The authenticated Slack adapter described below supplies read-only capture; live provisioning remains separate. Same source and bytes replay safely; edited signals need new source identities. Candidate text is data and cannot approve an amendment.

`plan(identity, amendment, authority)` appends immutable versions. An amendment contains `impact`, `bindings` (each `task`, `spec`, `revision`) and explicit `supersedes` revision hashes. The protected feedback authority document has `repository`, approved `specs` with `sha256`/`task_ids`, and `feedback_amendments` mapping the feedback identity to SHA-256 of canonical amendment JSON (`digest.canonical`). This is a separate operator approval contract; do not insert it into `factory/policy.json` without extending that schema through protected review. Approve the complete impact and supersession scope, import the approved ledger tasks, then call plan. The module does not invent tasks or approve specs. New task IDs/revisions preserve historical work. Superseded nonterminal work is blocked/fenced and in-flight outbox effects become uncertain; reconcile actual remote outcomes. Fencing does not undo an already completed external action or instantly kill a worker; the supervisor observes revoked authority and performs cleanup.

`reconcile(identity)` requires all current amendment bindings to have matching authenticated delivery receipts/provenance previously ingested by `factory-receipts.py`. Local `[x]` or runtime merged markers alone are insufficient. Multi-spec partial delivery stays planned. Complete delivery becomes delivered, with history retained. `accept(identity, operator, source_ref)` records separate explicit operator acceptance after full delivery. Remote approval and acceptance authentication belong to a separately protected operator adapter. A changed requirement after acceptance is a new signal, retaining the earlier record.

`post-ship-close-feedback.sh <spec-id>` requires existing absolute `FACTORY_RUNTIME_DB` and `FACTORY_REPOSITORY`, then reconciles registered feedback from receipts. Without configuration it fails visibly. It does not sed-edit or move historical markdown entries. Migrating/projecting the legacy registry, authenticated approval/acceptance and live Slack provisioning remain subsequent F-06 work; do not claim the entire feedback loop is active.

Persistent runtime and reporting state may be on separate protected hosts. Provision an authenticated read-only reporting source or a verified immutable delivery export before connecting them; this slice assumes locally accessible protected databases and does not copy state through candidate artifacts. Rollback is a protected revert PR preserving SQLite tables/events and original feedback. No real feedback intake, operator acceptance, supersession or Slack send occurs in fixture verification.

## Authenticated Slack ingress (030)

Spec 030 adds a read-only adapter for the protected reporting destination. Explicit top-level commands are `factory feedback #12,#13 enhancement: your exact feedback` and `factory hotfix #12 defect: urgent repair request`. Other kinds are defect, requirement, priority and acceptance. Thread replies, bots and unallowlisted senders are ignored. Malformed explicit commands from an allowlisted operator block the batch. All referenced PRs must belong to one confirmed report with its exact remote Slack receipt. Edits create immutable new source versions; deleted or unavailable messages cannot be reconstructed.

Run `python3 .claude/scripts/factory-slack-feedback.py --config /absolute/private/feedback.json` only in a trusted coordinator. Its protected config extends the hosted reporting configuration with `feedback_enabled: true`, an explicit `operators` list of Slack member IDs, an aware `feedback_start`, canonical absolute `private_root`, `runtime_database` directly inside that root and `implementation_roots` covering every implementation checkout. The root must already exist, belong to the coordinator and have mode 0700; config and existing runtime database must belong to it and have mode 0600. State inside an implementation checkout or symlink paths are rejected. Repository, state repository, branch, team and destination must match the protected source report configuration.

Filesystem modes alone do not isolate processes sharing the same OS identity. Use a separate coordinator principal and access boundary that prevents implementation agents from reading or modifying its credentials, config and runtime state. The operator allowlist is protected configuration, never obtained from messages or display names. Slack credentials stay in the coordinator environment under the configured `token_env`; GitHub read credentials use FACTORY_REPORTING_STATE_TOKEN or GH_TOKEN. Do not extract GitHub Actions secrets for local use, publish raw feedback in workflow logs, artifacts or the public reporting branch, or enable ingress without this boundary.

The poller reads Slack and GitHub without posting or committing. It imports the validated public report snapshot into a temporary private reporting projection, then commits the complete feedback batch atomically to private runtime SQLite. Source identities bind team, channel and exact timestamp; authenticated edits add the edit timestamp. Replays retain existing immutable rows. Hotfixes add an urgency event only: planning, protected amendment approval, implementation, independent review, evidence and merge gates still apply. An acceptance command is captured as open feedback; only the separate authenticated acceptance transition can accept a feature.

Each poll scans from the protected start, bounded to 100 pages and 1,000 captured commands. Exceeding bounds blocks instead of dropping feedback. A future retention/checkpoint migration must preserve immutable source history. CLI output contains feedback IDs and count only. Local fixtures prove the contract; live ingress remains disabled pending the operator member ID and isolated runtime provisioning.
