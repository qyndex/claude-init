# Operator feedback and amendments

The reusable feedback core lives in `.claude/scripts/factory-feedback.py`. Its SQLite tables are a protected runtime projection, not a replacement for `tasks/TASKS.md`. The APIs run only within the trusted operator/coordinator boundary. They are not a network endpoint. Candidate code must not write this database or the approval document.

`Feedback(database, repository).intake(reporting_database, document)` requires a confirmed digest from the protected reporting database and explicit PR identities in that report. Documents retain exact text, reporter, classification (`defect`, `enhancement`, `requirement`, `priority`, `acceptance`), source reference, digest key and repository. Source references must come from an authenticated operator adapter; a caller-supplied reporter string alone does not establish authentication. The current slice provides no live Slack poller. Same source and bytes replay safely; edited signals need new source identities. Candidate text is data and cannot approve an amendment.

`plan(identity, amendment, authority)` appends immutable versions. An amendment contains `impact`, `bindings` (each `task`, `spec`, `revision`) and explicit `supersedes` revision hashes. The protected feedback authority document has `repository`, approved `specs` with `sha256`/`task_ids`, and `feedback_amendments` mapping the feedback identity to SHA-256 of canonical amendment JSON (`digest.canonical`). This is a separate operator approval contract; do not insert it into `factory/policy.json` without extending that schema through protected review. Approve the complete impact and supersession scope, import the approved ledger tasks, then call plan. The module does not invent tasks or approve specs. New task IDs/revisions preserve historical work. Superseded nonterminal work is blocked/fenced and in-flight outbox effects become uncertain; reconcile actual remote outcomes. Fencing does not undo an already completed external action or instantly kill a worker; the supervisor observes revoked authority and performs cleanup.

`reconcile(identity)` requires all current amendment bindings to have matching authenticated delivery receipts/provenance previously ingested by `factory-receipts.py`. Local `[x]` or runtime merged markers alone are insufficient. Multi-spec partial delivery stays planned. Complete delivery becomes delivered, with history retained. `accept(identity, operator, source_ref)` records separate explicit operator acceptance after full delivery. Remote authentication belongs to the future intake adapter. A changed requirement after acceptance is a new signal, retaining the earlier record.

`post-ship-close-feedback.sh <spec-id>` requires existing absolute `FACTORY_RUNTIME_DB` and `FACTORY_REPOSITORY`, then reconciles registered feedback from receipts. Without configuration it fails visibly. It does not sed-edit or move historical markdown entries. Migrating/projecting the legacy registry and authenticated live Slack intake are subsequent F-06 work; do not claim the entire feedback loop is active.

Persistent runtime and reporting state may be on separate protected hosts. Provision an authenticated read-only reporting source or a verified immutable delivery export before connecting them; this slice assumes locally accessible protected databases and does not copy state through candidate artifacts. Rollback is a protected revert PR preserving SQLite tables/events and original feedback. No real feedback intake, operator acceptance, supersession or Slack send occurs in fixture verification.
